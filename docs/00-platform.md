# 00 — Platform SDD

> Scope: conventions and contracts shared by all six Sodales applications. App-specific behavior
> lives in each app's SDD (01–06). Decisions and their rationale live in `decision-log.md`.

## 1. Purpose

Host six independent Sodales products (Main portfolio, Academy, Persona, Cinema, Talents, Store)
in one repository with one shared UI foundation, while keeping runtime, data, and authentication
fully isolated per app.

## 2. Target users

Public visitors and authenticated users/admins per app; the Sodales team as content admins.

## 3. Platform roles

No platform-wide roles exist. Every app defines and enforces its own roles server-side.

## 4. Monorepo layout

```
sodales/
├── apps/
│   ├── main/       (port 3000, no DB)
│   ├── academy/    (port 3001, sodales-academy)
│   ├── persona/    (port 3002, sodales-persona)
│   ├── cinema/     (port 3003, sodales-cinema)
│   ├── talents/    (port 3004, sodales-talents)
│   └── store/      (port 3005, sodales-store)
├── packages/
│   └── ui/         (shadcn/ui primitives + design tokens)
├── docs/
│   ├── SODALES-IMPLEMENTATION.md
│   └── sdd/        (00-platform, 01–06 per app, decision-log)
├── docker-compose.yml
├── Dockerfile
├── Makefile
├── turbo.json
└── pnpm-workspace.yaml
```

Deliberately absent: shared `packages/auth`, `packages/db`, `packages/types`. Each app owns its
auth integration, schema, and data access. Only visual primitives are shared.

## 5. App structure contract (DB-backed apps)

```
apps/<app>/src/
├── app/          (App Router routes)
├── auth/         (Neon Auth client, session helpers, role guards)
├── db/
│   ├── index.ts  (Drizzle client — server-only)
│   ├── schema/   (per-domain schema files)
│   ├── migrations/
│   └── seed.ts   (dev/preview seed incl. first-admin bootstrap)
├── components/   (app-local UI)
├── features/     (business logic per domain)
└── lib/          (validation, utils, constants)
```

Main omits `auth/` and `db/` for the MVP.

## 6. Auth pattern (per DB app)

- Neon Auth (managed Better Auth) provisioned per project on `main` first; dev branches inherit.
- Env contract: `DATABASE_URL`, `NEON_AUTH_BASE_URL`, `NEON_AUTH_COOKIE_SECRET`, `ADMIN_EMAIL`.
- Auth users live in the `neon_auth` schema; app role data lives in app tables keyed by auth user id.
- All session lookups and role checks run server-side (server components / server actions).
- Cookies: HTTP-only, secure, host-only. Never a shared parent domain.
- First admin: `ADMIN_EMAIL` + seed script promotes that user. Documented per app.
- Trusted domains: register every origin (previews, production, localhost policy) via
  `neon neon-auth domain add` before traffic is pointed at it.

## 7. Data conventions

- Drizzle ORM; snake_case table/column names; UUID primary keys.
- Slugs unique where public-facing; enforced by unique indexes.
- Timestamps: `created_at` / `updated_at` on mutable tables.
- Draft/publish lifecycle uses a `status` enum column, not a boolean.
- Migrations generated by Drizzle Kit; never hand-edited after being committed; applied via
  `make db-migrate APP=<app>` against the dev branch during development.
- App-role mapping tables (e.g. `user_profile`, `talent_profile`) carry the `role` value used
  by server-side authorization.

## 8. UI conventions

- shadcn/ui primitives in `packages/ui`; Tailwind design tokens shared via the package.
- Every workspace includes `components.json` so shadcn CLI additions resolve to the
  shared package instead of silently creating divergent app-local primitives.
- Apps may theme tokens but not fork primitives; app-specific business components stay local.
- Inter is the shared UI/body face. App-specific display faces are permitted for
  expressive editorial content according to `docs/brand/app-visual-directions.md`.
- Every list view: loading, empty, error states. Every form: validation, success, error states.
- Responsive at mobile and desktop; keyboard navigable; semantic landmarks; labeled inputs.

## 9. Environments

| Environment | Database target             | Env source                    |
| ----------- | --------------------------- | ----------------------------- |
| Local dev   | Neon `dev` branch (Docker)  | `apps/<app>/.env.local`       |
| Preview     | Auto Neon branch per PR     | Vercel preview env            |
| Production  | Neon `main` branch          | Vercel production env         |

Vercel function region `sin1` (matches Neon Singapore). Secrets never leave server env.

## 10. Quality gates

- `make lint` / `make typecheck` / `make build` must pass (CI runs these per PR via Turborepo).
- Vitest for unit tests (validation, role logic); Playwright smoke per app as it matures.
- PR template: SDD reference, acceptance checklist, preview URL, screenshots, migration notes,
  test results, a11y check, owner review.
- Reviewer pass: an independent reviewer audits implementation vs SDD + auth/authorization
  security review before merge.

## 11. Acceptance criteria (platform)

- [ ] Six apps scaffold with pinned dev ports and shared UI package
- [ ] `make dev` brings up all six apps; `make rebuild` rebuilds cleanly
- [ ] No secret values appear in git history, docs, or `.env.example`
- [ ] CI runs lint/typecheck/build on PRs
- [ ] Each DB app: dev branch + Neon Auth + env files + first-admin bootstrap
- [ ] All docs in `docs/` current with verified project IDs

## 12. Test plan (platform)

- Lint/typecheck/build in CI per PR.
- Per-app: unit tests for validation + authorization logic; E2E smoke for auth loop + one
  public flow; visual check of rendered pages before owner review.

## 13. Deployment requirements

One Vercel project per app (`sodales-main`, `sodales-academy`, …) with root directories set;
production env vars per app; `sin1` region; previews isolated per PR. DNS only after the final
base domain is confirmed.

## 14. Open decisions

- Final base domain (blocks production DNS only; previews unaffected).
- Main contact-form delivery provider confirmation (Resend assumed; see decision log).

## 15. Risks

- Neon Auth env-var/SDK naming drift — verify against current Neon docs at wiring time.
- Five auth islands = five registrations per user (accepted MVP tradeoff).
- Team members new to Turborepo/Neon branching — mitigated by Makefile wrappers and this SDD.
