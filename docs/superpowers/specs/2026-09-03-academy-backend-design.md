# Sodales Academy — Phase 2 Backend Design

## 1. Purpose

Swap Phase 1's filesystem/cookie/`localStorage` seam for a real backend: Postgres persistence,
real Google OAuth + invite-code auth, and server-enforced authorization — without rewriting any
page, component, or layout. Phase 1 (`docs/superpowers/specs/2026-09-03-academy-frontend-design.md`)
was built specifically so this would be a body-swap behind `src/lib/content/queries.ts` and
`src/lib/session.ts`, not a rewrite; this spec is that swap.

## 2. Scope

### In scope

- Neon Postgres + Drizzle ORM schema for courses, modules, lessons, enrollments, progress, and
  user profiles.
- Neon Auth (managed Better Auth) with Google as the only OAuth provider, gated by a DB-backed
  shared invite code.
- Swapping `queries.ts`/`session.ts` bodies for real reads; adding `mutations.ts` (new) for
  writes that Phase 1 only ever toasted about.
- Wiring the existing admin course form, publish/unpublish/delete, and the learner-facing enroll/
  mark-complete actions to actually persist.
- A one-time migration that imports the 4 courses / 19 lessons already authored in
  `content/courses/` into Postgres, then deletes `content/` and `src/lib/content/loader.ts`.

### Out of scope (separate specs, once this lands)

Enrolled-only lesson comments (D-1), a Tiptap lesson editor replacing the plain-text/Markdown
`Textarea`, branch-per-PR Neon preview infrastructure, video hosting, payments, certificates,
quizzes, email notifications.

## 3. Repository structure

Standalone repo stays standalone — no migration into the `docs/00-platform.md` six-app monorepo.
`docs/00-platform.md`/`docs/02-academy.md`'s conventions (Drizzle, Neon Auth pattern, env
contract, data model) are adopted adapted for a single standalone app: no `apps/<app>/` prefix,
no `packages/ui`, no port pinning, no `make` commands.

```
sodales/
├── src/
│   ├── db/
│   │   ├── index.ts          # Drizzle client, server-only
│   │   ├── schema/
│   │   │   ├── user.ts       # user_profile
│   │   │   ├── course.ts     # course, course_module, lesson
│   │   │   ├── enrollment.ts # enrollment, lesson_progress
│   │   │   └── invite.ts     # invite_code
│   │   ├── migrations/       # generated by drizzle-kit, never hand-edited
│   │   └── seed.ts           # first-admin promotion + content/ migration (§7)
│   ├── lib/
│   │   ├── auth/
│   │   │   └── server.ts     # createNeonAuth instance, Google-only provider
│   │   ├── content/
│   │   │   ├── types.ts      # unchanged
│   │   │   ├── queries.ts    # same signatures, Drizzle SELECTs
│   │   │   └── mutations.ts  # NEW — Server Actions for every write
│   │   ├── session.ts        # same signatures, real Neon Auth + user_profile reads
│   │   └── validation.ts     # gains instructorUserId on courseInputSchema
│   └── app/
│       └── api/auth/[...path]/route.ts   # Neon Auth handler
```

**Deleted:** `content/`, `src/lib/content/loader.ts`, `src/lib/progress.ts`, `src/content/session.ts`,
`NEXT_PUBLIC_DEMO_MODE`, the role-switcher cookie, `<RoleSwitcher />`, and its "Reset demo progress"
action. Real sessions and real persistence make every one of these obsolete — they aren't ported
forward or kept as fallbacks.

## 4. Stack

Neon Postgres · Drizzle ORM + Drizzle Kit · Neon Auth (managed Better Auth) · Google OAuth ·
everything else unchanged from Phase 1 (Next.js 16.3, React 19.2, TypeScript strict, Tailwind v4.3,
shadcn/ui, zod v4, pnpm, Vitest, Vercel `sin1`).

## 5. Data model

All tables UUID PKs, `snake_case`, `created_at`/`updated_at` on mutable tables. Auth users live in
`neon_auth."user"` — no cross-schema FK is possible; the link is enforced in code via
`user_profile.user_id`.

| Table | Columns | Notes |
| --- | --- | --- |
| `user_profile` | `id`, `user_id` (unique, NOT NULL), `name` (NOT NULL), `role` enum `user_role` default `learner` | one row per auth user |
| `course` | `id`, `slug` (unique NOT NULL), `title`, `description`, `category`, `level` enum `course_level`, `status` enum `course_status` default `draft`, `instructor_user_id` (NOT NULL) | admin manages any course; instructor manages only their own |
| `course_module` | `id`, `course_id` → course CASCADE, `title`, `position` (int) | ordered by position |
| `lesson` | `id`, `module_id` → course_module CASCADE, `course_id` → course CASCADE, `slug`, `title`, `content` (text), `position` (int), `is_preview` (bool default false) | `unique(course_id, slug)` |
| `enrollment` | `id`, `course_id` → course CASCADE, `user_id`, `enrolled_at` default now | `unique(course_id, user_id)` — explicit per-course enrollment, not automatic account-wide access |
| `lesson_progress` | `id`, `lesson_id` → lesson CASCADE, `user_id`, `completed_at` default now | `unique(lesson_id, user_id)` — replaces `localStorage` entirely |
| `invite_code` | `id`, `code` (unique NOT NULL, hashed), `created_at`, `revoked_at` (nullable) | supports rotation without a redeploy; §6 |

Enums: `user_role` (`learner`, `instructor`, `admin`), `course_level` (`beginner`, `intermediate`,
`advanced`), `course_status` (`draft`, `published`).

`courseInputSchema` in `src/lib/validation.ts` gains `instructorUserId: z.string().uuid()`
(admin-settable in the form; the server always overwrites it with the session user's id when the
submitter is an instructor, so an instructor can never assign a course to someone else).

## 6. Auth: Neon Auth, Google OAuth, invite code

- `src/lib/auth/server.ts` — `createNeonAuth`, Google as the only provider. No email/password
  provider — Phase 1's disabled login form and deviation D-2 both rule that out.
- Handler at `src/app/api/auth/[...path]/route.ts`, per `docs/00-platform.md` §6.
- **Invite code is code-first.** The sign-up page's invite-code field posts to a Server Action
  that checks the submitted code against `invite_code` (hashed comparison, `revoked_at IS NULL`).
  On success it signs a short-lived HMAC token (code id + timestamp) into a cookie. **Continue
  with Google** only enables once that cookie exists. The OAuth callback re-verifies the signed
  token server-side before creating the `user_profile` row — a forged or expired token never
  grants access, and the raw invite code itself never has to survive a redirect through Google's
  servers.
- Sign-up creates the Neon Auth user **and** the `user_profile` row (role `learner`) in the same
  server-side flow. If the profile insert fails after the auth user was created, the callback
  reports an explicit setup error rather than silently leaving a profile-less account that can
  authenticate but never resolves a role.
- Session helpers keep their Phase 1 signatures — `getSession` (React-cached), `requireUser`
  (redirect `/login`), `requireRole(...roles)` (redirect `/`) — bodies swap to read the real Neon
  Auth session and join `user_profile` for role.
- Signed-in users visiting `/login` or `/sign-up` redirect to `/dashboard`.
- First admin: `src/db/seed.ts` promotes one `ADMIN_EMAIL` env var's user to `role: "admin"` if
  they've already signed up (idempotent — safe to re-run, no-ops if the user doesn't exist yet or
  is already admin). Since sign-up is no longer open, this is a one-off promotion step run once
  after `ADMIN_EMAIL` completes the normal invite-code + Google sign-up, not account creation.

## 7. Content migration

`src/db/seed.ts`, run once against a fresh database, inside a single transaction:

1. Promote `ADMIN_EMAIL` to admin if that user has signed up (§6).
2. Reuse the frontmatter/Markdown parsing logic from Phase 1's `src/lib/content/loader.ts` to walk
   `content/courses/*` one last time, inserting every course/module/lesson into Postgres exactly
   as authored — same slugs, same `isPreview` flags, same `status` (the `test-fixture-course`
   fixture imports too, staying a draft, since it's still useful for exercising draft-visibility
   rules against real data rather than static fixtures).
3. All four migrated courses default `instructor_user_id` to `ADMIN_EMAIL`'s user; reassignable
   afterward through the edit form.

Once this succeeds in production, `content/` and `src/lib/content/loader.ts` are deleted in the
same PR — nothing depends on the Markdown files afterward.

## 8. Authorization & mutations

One invariant everywhere (`docs/02-academy.md` §11): an admin may manage any course; an instructor
may manage only a course whose `instructor_user_id` is their own session user id. Draft
visibility, edit, publish/unpublish, delete, and lesson access all reuse this same rule via
`assertCanManageCourse(courseId, viewer)`.

`src/lib/content/mutations.ts` — Server Actions, one per write:

- `createCourse`, `updateCourse` — run `courseInputSchema.safeParse` server-side before touching
  the DB (the admin form's client-side validation is a UX nicety, not the source of truth).
- `publishCourse` / `unpublishCourse`, `deleteCourse` (with the existing confirm `Dialog`).
- `enrollInCourse` — explicit per-course enrollment; `onConflictDoNothing` on
  `unique(course_id, user_id)` makes a double-click a safe no-op.
- `toggleLessonComplete` — writes/deletes a `lesson_progress` row; same `onConflictDoNothing`
  safety.

Every action re-derives session/role server-side and never trusts a client-supplied role or
ownership claim. Lesson reads are two-step: metadata first (resolves published/draft, role,
ownership, preview status, enrollment), `lesson.content` fetched only once access is confirmed —
an unauthorized request never receives the lesson body at all. Slug collisions against *other*
courses are rejected server-side with a friendly field error; the DB's unique constraint is the
backstop, not the primary check.

## 9. Error handling

- Unknown course/lesson slugs → `notFound()`.
- Forbidden role/ownership in pages → `redirect("/")`; in Server Actions → thrown errors converted
  to `{ ok: false, message }`, surfaced as error toasts (distinct from Phase 1's demo-mode toasts
  — these represent real failures now that writes are real).
- Zod failures in actions → first issue's message returned inline + toast, same UX as Phase 1's
  client-only validation.
- DB unique-slug violations → friendly "Slug already in use" field error.
- `error.tsx` keeps its Phase 1 retry affordance.

## 10. Testing

- Vitest: the migration/seed parser (reusing Phase 1's loader test fixtures), `mutations.ts`
  authorization logic (instructor can't touch another instructor's course; admin can touch
  anything; unauthenticated/wrong-role calls are rejected before any write), `validation.ts`
  (existing coverage plus `instructorUserId` cases).
- `pnpm typecheck && pnpm lint && pnpm build` stay the required gate. `generateStaticParams` on
  `/courses/[slug]` and the lesson route currently prerenders against static Markdown at build
  time; once course/lesson data is a runtime DB read, the plan needs to confirm whether those
  routes stay statically prerendered (build-time DB read) or become fully dynamic, and update
  accordingly.
- E2E still deferred.

## 11. Deployment / environments

Staying on `main`, no branch-per-PR Neon previews for now (single owner, per your answer) — one
Neon branch is enough. Env contract grows to: `DATABASE_URL`, `NEON_AUTH_BASE_URL`,
`NEON_AUTH_COOKIE_SECRET`, `ADMIN_EMAIL`, Google OAuth client id/secret. `NEXT_PUBLIC_DEMO_MODE`
is deleted along with the role switcher.

**External dependency with lead time:** a Google Cloud OAuth client for production sign-in needs a
published consent screen, which takes several days. This should be requested as an early,
parallel step in the implementation plan — it doesn't block schema/migration work, but blocks
testing the real sign-up flow end-to-end.

## 12. Acceptance criteria

- [ ] `pnpm typecheck && pnpm lint && pnpm build` all green
- [ ] `src/db/seed.ts` migrates all 4 courses / 19 lessons + the draft fixture into Postgres,
      idempotently, inside a transaction
- [ ] Sign-up requires a valid, unrevoked invite code before Google OAuth can even be attempted;
      an invalid/expired code never reaches the Google redirect
- [ ] `ADMIN_EMAIL` becomes `role: "admin"` after signing up and running the seed promotion step
- [ ] Instructor role can create/edit/publish/unpublish/delete only their own courses; attempting
      another instructor's course is rejected server-side, not just hidden in the UI
- [ ] Admin role can manage any course regardless of `instructor_user_id`
- [ ] A learner can enroll in a published course, mark lessons complete, and see it reflected on
      `/dashboard` after a real page reload (no `localStorage` involved)
- [ ] An unauthenticated or unenrolled request for a lesson's content never receives
      `lesson.content` in the response, even if it can see the lesson's metadata
- [ ] `content/`, `src/lib/content/loader.ts`, `src/lib/progress.ts`, `src/content/session.ts`,
      `NEXT_PUBLIC_DEMO_MODE`, and the role switcher are all deleted, not left as dead code
- [ ] Deployed and reachable on the existing production Vercel URL with real data

## 13. Open items

1. **`generateStaticParams` classification** (§10) — needs resolving during planning, not here.
2. **Invite code rotation UX** — this spec puts codes in a DB table so an admin *can* rotate one
   without a redeploy, but doesn't design an admin UI for creating/revoking codes. Minimal
   version (a seed-inserted single code, rotated by direct DB access) is enough to ship; a
   proper admin UI for it is a fast-follow, not a blocker.
3. **Google Cloud OAuth consent screen** — external, multi-day lead time (§11); should be
   requested immediately regardless of when code work starts.
4. **Comments (D-1) and the Tiptap editor** — explicitly deferred to their own specs once this
   lands (per your scope answer, §2).

## 14. Risks

| Risk | Mitigation |
| --- | --- |
| Neon Auth is Beta (Better Auth 1.4.18) | Verify current Neon docs at wiring time, same caveat Phase 1's spec already flagged |
| Signed invite-code token forged or replayed | HMAC-signed with a server secret, short-lived, re-verified server-side in the OAuth callback — never trust the cookie's presence alone |
| Migration partially fails, leaving a half-seeded catalog | Runs inside a single transaction (§7) — all-or-nothing |
| `generateStaticParams` classification change breaks the build in a way Phase 1's build never exercised | Caught by the existing `pnpm build` gate before merge; plan should build this early and re-verify, not defer it to the end |
